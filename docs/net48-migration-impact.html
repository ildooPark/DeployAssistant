DeployAssistant · 이전 영향 분석

net48로 내려갈 것인가

추정하지 않고 실제로 다운그레이드해서 측정했다. 컴파일 비용은 예상보다 훨씬 싸다 — shim 파일 하나, LangVersion 두 줄, TFM 다섯 개. 하지만 그 대가로 무결성 도구가 260자 넘는 경로에서 조용히 틀린 답을 내게 된다.

측정일 2026-08-20 GUI 3.8.0 · CLI 1.2.0 Windows 11 26200 LongPathsEnabled = 0

결론

이전 자체는 값싸다. 문제는 이전이 무엇을 잃게 하느냐다. 전체 솔루션을 net48로 돌렸을 때 컴파일 에러는 단 3개, 모두 같은 원인(OpenFolderDialog)이었고, shim 하나로 해결됐다. 테스트 478개 전부 통과, GUI 정상 실행, CLI 스모크 통과.

그런데 net48을 정당화하던 근거가 이번 측정에서 사라졌다. 페이로드 절감이 이유였는데, AvalonDock·Xceed를 걷어낸 지금 net48(zip 2.18 MB)은 net8 framework-dependent(1.88 MB)보다 오히려 크다. 패키지 자산 논쟁도 대상이 없어졌다.

남은 순이득은 시작 70 ms와 유휴 메모리 50 MB다. 잃는 것은 긴 경로 처리 능력, 1.4배 느린 파일 열거, 2–3배 느린 JSON, 그리고 직접 관리해야 하는 COM 폴더 선택기다.

01 — 이전 비용

실제로 해봤고, 거의 공짜였다

스크래치 사본에서 5개 프로젝트의 TFM을 전부 net48로 바꾸고 빌드했다. 감시 목록에 올려둔 위험 API는 단 하나도 걸리지 않았다.

이유는 명확하다. DeployAssistant.Core가 netstandard2.0을 타깃하고 있고, 이건 net48 표면의 진부분집합이다. 즉 코드베이스는 이미 오래전부터 모던 BCL API를 쓸 수 없는 상태였다. Path.GetRelativePath와 Dictionary.TryAdd는 이미 CompatHelper.cs에 폴리필돼 있고, IsExternalInit shim도 Core와 CLI에 이미 있다.

유일한 컴파일 에러 — 3곳, 동일 원인DeployAssistant\Services\WpfDialogService.cs(32,27): error CS0246: 'OpenFolderDialog' 을(를) 찾을 수 없습니다 DeployAssistant\ViewModel\FileTrackViewModel.cs(144,41): error CS0246: ... DeployAssistant\ViewModel\MetaDataViewModel.cs(155,30): error CS0246: ...

Microsoft.Win32.OpenFolderDialog는 .NET 8 WPF 전용이다. PR #20에서 WinForms를 걷어내며 FolderBrowserDialog를 대체한 그 API다. Win32 IFileOpenDialog + FOS_PICKFOLDERS로 약 145줄짜리 shim을 만들면 호출부는 한 줄도 안 바꿔도 된다 — .NET 8이 내부적으로 하는 것과 같은 일이다.

shim 적용 후 최종 빌드 1031 Warning(s) 0 Error(s) Time Elapsed 00:00:01.81 Passed! - Failed: 0, Passed: 356, Skipped: 0, Total: 356 - DeployAssistant.Tests.dll (net48) Passed! - Failed: 0, Passed: 122, Skipped: 0, Total: 122 - DeployAssistant.CLI.Tests.dll (net48) GUI: HasExited=False MainWindowTitle=[Deploy Assistant v3.8.0] Responding=True CLI: --help EXITCODE=0 · no-args EXITCODE=0 · unknown EXITCODE=1

경고는 net8 대조군 대비 +2개뿐이고, 그 2개마저 전부 shim에서 나온 CS8601(nullable 대입)이다. 릴리즈 게이트가 "V1-obsolete 외 신규 경고에서 중단"이므로 이건 고치고 넘어가야 한다.

숨은 취약점 실측

GUI의 4곳이 string.Contains(string, StringComparison)를 쓴다. 이 오버로드는 net48에 없다(단독 프로브에서 CS1501 확인). 그런데도 컴파일되는 이유는 System.Memory 4.5.5가 확장 메서드로 공급하기 때문이고, GUI는 그 패키지를 직접 참조하지 않는다 — Core → System.Text.Json → System.Memory로 전이돼 온다.

즉 선언하지도 않은 의존성의 전이 패키지에 컴파일이 걸려 있다. 나중에 Core에서 System.Text.Json을 걷어내면 전혀 무관한 UI 파일 4개가 알 수 없는 CS1501로 깨진다. net48로 간다면 System.Memory를 명시적으로 참조해야 한다.

02 — CLI

CLI는 아무것도 안 바뀐다. 이미 net48에서 돌고 있으니까

CLI는 이미 net472이고 Core는 netstandard2.0이다. netstandard2.0은 참조 전용 계약이라 런타임에는 mscorlib로 그대로 타입 포워딩된다 — netstandard BCL 구현체 같은 건 없다. 그래서 CLI의 File.*, Directory.*, MD5.*는 오늘 이미 .NET Framework BCL에서 실행되고 있다.

프로브가 직접 확인해준다. net472 앱이 보고하는 RuntimeVersion은 이미 4.8이다. net472와 net48의 차이는 컴파일 타임 참조 어셈블리와 TargetFrameworkAttribute일 뿐이고, 머신은 어느 쪽이든 in-place 4.8 런타임 하나를 돌린다.

동일 프로브 · 동일 Core · 동일 코퍼스 — (A) 오늘의 CLI vs (C) Core까지 net48### (A) net472 = 오늘 출하 중인 CLI (Core=netstandard2.0) File.Exists(deep) : False HashTool.GetFileMD5CheckSum(root, DEEPrel) : "" Directory.GetFiles(root,*,AllDirectories).Length : 1 ProjectScanner.EnumerateFiles(root).Count() : 1 ### (C) net48 (Core도 net48로 전환) File.Exists(deep) : False HashTool.GetFileMD5CheckSum(root, DEEPrel) : "" Directory.GetFiles(root,*,AllDirectories).Length : 1 ProjectScanner.EnumerateFiles(root).Count() : 1

한 줄도 다르지 않다. 패키지 자산도 전부 동일하게 해결된다. CLI에 관한 한 net472 → net48은 완전한 no-op이며, 달라지는 건 요구 런타임 최소치가 4.7.2에서 4.8로 올라가는 것뿐이다.

Spectre.Console 0.49.1은 lib/에 net6.0 · net7.0 · net8.0 · netstandard2.0만 있고 net4x 자산이 없다. 양쪽 다 netstandard2.0으로 떨어져 동일하다 — 교체 불필요.

그런데 이게 좋은 소식이 아니다 중요

"CLI는 안 바뀐다"는 말은 곧 긴 경로 버그가 CLI에는 이미 오늘 존재한다는 뜻이다. 미래의 위험이 아니라 출하 중인 net472 빌드의 현재 상태다.

매니페스트로도 못 고친다

longPathAware 애플리케이션 매니페스트와 AppContext 스위치(UseLegacyPathHandling=false, BlockLongPaths=false)를 붙인 변형(B)을 따로 빌드해 돌렸다. 결과는 순수 net472와 완전히 동일했다. LongPathsEnabled=0이면 OS가 여전히 MAX_PATH를 강제하기 때문이다.

.NET Core/8은 내부적으로 \\?\를 붙여 이 전부를 우회한다. 긴 경로 지원은 net472 대 net48의 문제가 아니라 .NET 플레이버 자체의 속성이다. GUI를 net48로 내리는 것은 곧 GUI에게 CLI가 이미 가진 버그를 넘겨주는 일이다.

그리고 실제 피해는 "조용함"보다 나쁘다

깊은 경로의 파일은 애초에 열거되지 않으므로 intersectFiles에 들어가지 못한다. 즉 메타데이터 폴백 검증에 도달조차 못 한다. 그 다음에 무슨 일이 일어나는지는 스냅샷을 누가 만들었느냐에 갈린다.

1
GUI(net8)가 스냅샷 생성370자 파일이 정상적으로 기록됨
2
CLI(net472)가 무결성 검사디스크 열거에서 그 파일이 안 보임
3
집합 연산deletedFiles에 편입 — 메타데이터엔 있는데 디스크엔 없으니까
4
"has been Deleted" 로그디스크에 멀쩡히 있는 파일이 삭제됨으로 스테이징된다

이건 침묵이 아니라 적극적인 오보다. 사용자가 그 변경 기록을 보고 조치할 수 있다. CLI로 만든 스냅샷을 CLI로 검사하는 경우엔 반대로 완전한 침묵이다 — 초기화 때도 안 보였으니 어느 목록에도 없고, 해시된 적도 백업된 적도 배포된 적도 없으며 어떤 로그에도 나오지 않는다.

공정하게 짚을 점 실측

해시가 ""로 실패하는 일반적인 경우(잠긴 파일 등)는 설계가 제대로 돼 있다. FileManager.cs:237-240이 파일을 의도적으로 유지하고, :266-272가 VerifyByMetadata로 폴백하며, :1451이 "verified by metadata only" 로그를 남긴다. 이 경고는 GUI 로그 창과 CLI 화면에 실제로 도달한다.

문제는 긴 경로가 이 안전망 앞단에서 사라진다는 점이다. 폴백은 잘 만들어져 있는데, 그 코드까지 가지를 못한다.

04 — 성능

해싱은 그대로, 열거와 JSON은 느려진다

이 앱의 지배적 비용은 해싱인데, 거기서는 차이가 없다. MD5에는 CPU 명령어 가속이 없고(SHA-NI는 SHA-1/256만), 두 런타임 모두 Windows 네이티브 크립토를 쓴다 — net4x는 CAPI, net8은 CNG.

느려지는 두 항목 — 파일 열거와 JSON — 이 하필 이 앱이 해싱 다음으로 가장 많이 하는 일이다. 프로젝트를 열 때 큰 ProjectMetaData.bin을 역직렬화하는 비용이 16 MB당 약 +100 ms 늘어난다.

이전 측정과 방향이 뒤집힌 항목

메모리는 이전 조사에서 net48이 더 높게(340 vs 299 MB) 나왔는데 이번엔 더 낮게(131 vs 182 MB) 나왔다. 같은 측정이 아니다 — 이번 것은 프로젝트를 로드하지 않은 갓 열린 창이고, 이전 것은 3,000파일 코퍼스 부하 상태였을 가능성이 높다. 그 상태에선 net8 GC가 더 큰 gen0 예산으로 메모리를 써서 4배 적은 수집 횟수를 산다.

둘 다 참일 수 있다: net48은 가볍게 시작하고, net8은 부하에서 더 잘 확장된다. 부하 상태 메모리는 이번에 재측정하지 않았다.

05 — 도달 범위

어떤 기계에서 실제로 돌아가는가

"net48은 in-box"라는 말은 조건부로만 참이다. 마이크로소프트 공식 표 기준 확인:

즉 4.8이 진짜 기본 탑재되는 건 Windows 10 1903부터다. 1809 이하 기계에서는 net48 앱도 런타임 설치가 필요하고, Windows 8 RTM에서는 설치조차 불가능하다. Windows 8은 2016년 1월, 8.1은 2023년 1월에 지원이 끝났다.

Core를 netstandard2.0로 두는 이유 확인

netstandard2.0의 공식 최소치는 4.6.1이지만, 4.6.1은 netstandard2.0이 설계되기 전에 나온 버전이라 필요한 파일이 빠져 있어 추가 배포가 필요하고 알려진 문제가 있다. 추가 의존성 없이 온전히 지원하는 첫 버전은 4.7.2이며 MS 권장도 4.7.2+다. 게다가 4.6.1은 2022년 4월에 지원이 끝났다.

따라서 현실적인 범위는 4.7.2 ~ 4.8이다. CLI가 이미 net472이므로 그것이 곧 현재의 하한이기도 하다.

06 — 페이로드

net48을 정당화하던 근거가 사라졌다

전송 크기가 이유였다면, 이번 측정이 그 논거를 무너뜨린다.

형태원본 MBzip MB이전필요 런타임
net8 self-contained 단일파일 — 현재 릴리즈161.0664.4264.4없음

AvalonDock·Xceed 제거로 net48 zip이 0.82 MB(−27%) 줄었다. 그런데 그러고도 net8 framework-dependent가 더 작다. 즉 다운그레이드는 전송 크기 문제의 최선책이 아니라 차선책이다.

패키지 자산 논쟁도 끝났다. 이전에 net472를 피해야 했던 이유는 AvalonDock이 net40 자산으로 떨어지기 때문이었는데, AvalonDock이 사라진 지금 그래프의 모든 패키지가 net472와 net48에서 동일한 자산으로 해결된다. 논쟁의 대상 자체가 없다.

진짜 범인은 따로 있다 실측

net8 FDD 페이로드는 파일이 8개뿐인데, 그중 DocumentFormat.OpenXml.dll 하나가 6.04 MB — 전체의 83.4%다. 동반 어셈블리까지 합치면 89.6%. 앱 자체 어셈블리 3개를 다 합쳐야 0.62 MB(8.5%)다.

용도는 ExportManager.cs:158과 :227 두 줄, XLSX 내보내기 하나뿐이다. 다른 모든 .cs를 뒤져도 OpenXml 타입은 0건. 그리고 이 DLL은 net35부터 netstandard2.0까지 모든 자산에서 6 MB대라 TFM을 바꿔서 줄일 수 있는 게 아니다.

09 — 부수 발견

이전 여부와 무관하게 고칠 것

  • FileHandlerTool.cs:496의 정리 누락. 임시 파일 삭제를 if (File.Exists(tempPath))로 가드하는데, net4x에서 260자 초과 경로면 실재하는 파일에도 false가 나온다. 그래서 ProjectMetaData.bin.tmp가 영영 안 지워진다. 지금은 쓰기 자체가 먼저 실패해서 드러나지 않을 뿐이다.
  • CLAUDE.md의 어셈블리 이름이 낡았다. "assembly name SimpleBinaryVCS"라고 돼 있는데 csproj에 <AssemblyName>이 없어서 실제 산출물은 DeployAssistant.exe다.
  • File.Replace는 안전하다. net48에 존재하고(FX 2.0+), 동작이 바이트 단위로 동일하며, Google Drive 마운트와 SMB 공유 양쪽에서 실측 통과했다. 볼륨을 넘으면 IOException이 나지만, 백업 경로가 항상 ProjectPath 하위라 프로덕션에서는 도달 불가능하다.
